# Expert FFN 执行时间 vs GPU SM 分配比例实验报告

**硬件**: NVIDIA Tesla V100S PCIe 32GB
**方法**: CUDA MPS (`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE`) 限制每个进程可用的 SM 比例
**Expert 权重形状**: w13=(1408, 2048), w2=(2048, 704)，FP16
**Ridge point**: ≈ 115 tokens（V100S: 130 TFLOPS / 1134 GB/s / 1.0 FLOP/byte）

---

## 核心结论

> **BW-bound（n < 115 token）时，减少 SM 分配对延迟几乎无影响；
> Compute-bound（n > 115 token）时，延迟与 1/SM% 近似线性反比。**

---

## "自然 SM%" 推导

**自然 SM%** = 不加任何 MPS 限制时，cuBLAS 为这次 FFN 启动的 thread block 总数 ÷ V100S SM 数 × 100%。

### 第一步：确定两次 GEMM 的矩阵维度

Expert FFN 由两次 `F.linear` 组成：

```
w13 GEMM:  output = x @ w13.T
  x    : (n, 2048)        # n = token 数
  w13  : (1408, 2048)  →  转置后 (2048, 1408)
  输出 : (n, 1408)
  ∴ M = n,  N = 1408,  K = 2048

w2 GEMM:   output = inter @ w2.T
  inter: (n, 704)
  w2   : (2048, 704)   →  转置后 (704, 2048)
  输出 : (n, 2048)
  ∴ M = n,  N = 2048,  K = 704
```

> 权重形状来自模型加载日志（TP=2 分片后）：w13=(1408,2048)，w2=(2048,704)。

### 第二步：计算 cuBLAS 启动的 thread block 数

cuBLAS 把输出矩阵按 tile 切分，每个 tile 对应一个 thread block：

```
blocks = ceil(M / TILE_M) × ceil(N / TILE_N)
```

V100S FP16 上 cuBLAS 常用 tile size 约为 **TILE_M = 128，TILE_N = 128**（由 microbench_quantization.py 的 wave boundary 实验逆推得出）。

因此：

```
w13 的 N-tile 数 = ceil(1408 / 128) = 11
w2  的 N-tile 数 = ceil(2048 / 128) = 16
```

M-tile 数随 token 数变化：`ceil(n / 128)`

### 第三步：除以 80 SMs 得到自然 SM%

V100S PCIe 32GB 有 **80 个 SM**（与普通 V100 相同；V100S 提升的是算力和带宽，不是 SM 数）。

```
自然 SM% = (M-tiles × (11 + 16)) / 80 × 100%
         = ceil(n / 128) × 27 / 80 × 100%
```

代入各 token 数：

| Token 数 | M-tiles | w13 blocks | w2 blocks | 总 blocks | 自然 SM% |
|---------|---------|-----------|----------|---------|--------|
| n=16    | ceil(16/128) = **1**  | 1×11=11 | 1×16=16 | **27**  | 27/80 = **34%** |
| n=128   | ceil(128/128) = **1** | 1×11=11 | 1×16=16 | **27**  | 27/80 = **34%** |
| n=512   | ceil(512/128) = **4** | 4×11=44 | 4×16=64 | **108** | 108/80 = **135%**（需 2 wave）|
| n=1024  | ceil(1024/128) = **8**| 8×11=88 |8×16=128 | **216** | 216/80 = **270%**（需 3 wave）|

n=16 和 n=128 的 M-tile 数相同（都是 1），因此自然 SM% 相同，均为 **34%**。

n=16 和 n=128 的自然 SM% 只有 34%，意味着即使给它 100% 的 SM，仍有 66% 的 SM 空闲——这正是 BW-bound 的直接原因。

## 分析

### n=16（BW-bound，自然 SM% = 34%）

- SM% 从 30% → 100%：执行时间 100 μs → 107 μs，**几乎无变化**。
- 因为该 GEMM 只需 27 个 blocks，30% MPS = 24 个 SM 就够并行处理完所有 blocks。
- SM% 低于 30% 才会因 SM 不足开始序列化，时间升高。
- **结论：给 BW-bound expert 多分 SM 资源完全无益。**

### n=128（near-ridge，自然 SM% = 34%）

- 30% 以下，时间随 SM% 明显下降（506→122 μs）；
  30%~100%，时间平稳（122→109 μs）。
- 这是 BW/compute 边界行为：SM 充足后切回带宽瓶颈，更多 SM 无用。

### n=512（compute-bound，自然 SM% = 135%）

- 整个曲线与 `1/SM%` 较接近线性，5% 时 7.9× 慢，符合 wave 排队理论。
- 自然 SM% = 135%，即使 100% MPS 也要跑 2 个 wave，时间为 141 μs。

### n=1024（compute-bound，自然 SM% = 270%）

- 5% 时 12.2× 慢；100% 时 178 μs（3.4 个 wave）。
- 斜率比 n=512 更陡，compute-bound 程度更深。

---

## 对 FusedMoE 的意义

```
ShareGPT 每 expert 每步接收 ~2–5 tokens（n=2~5）
→ 自然 SM% ≈ 34%（只需 27 blocks / 80 SM）
→ 即使将 SM 限制到 30%，执行时间几乎不变
→ 热门 expert 占更多 blocks，但 80 SMs 仍然绰绰有余
→ "资源竞争" 在 BW-bound 下是虚假竞争
```

真正的延迟瓶颈不是 SM 数量，而是 **HBM 带宽**（加载 8.25 MB 权重的时间固定约 104 μs）。

只有 token 数 ≥ 115（compute-bound 区域）时，SM 分配比例才对延迟有显著影响。

**硬件计数器实测结果**：

n	GEMM sm_efficiency
4–16	62–63%
32–64	61–68%
128	71%
256–512	80–82%
1024	80%
关键发现：

sm_efficiency 在 n=16 时就已经是 63%，不是之前理论估计的 34%，也不是 blocks/80 算出来的 240%。原因是 sm_efficiency 的定义是"每个 SM 有活跃 warp 的时间占比，对 80 个 SM 取平均"，而不是"有多少 SM 在工作"。63% 的含义是：一次 GEMM 执行期间，80 个 SM 平均有 63% 的时钟周期处于活跃状态。

这个值随 n 增大缓慢上升（63% → 82%），而不是之前预想的从很低到很高，说明即使是小矩阵，cuBLAS 的 split-K 策略已经让大部分 SM 都有工作可做——只是每个 SM 的活跃度不够满（因为带宽瓶颈，SM 大量时间在等内存）。
